# Homura Looking Glass Agent

**English** | [简体中文](README.zh-CN.md)

`hlg-agent` is the node-side component of Homura Looking Glass. It runs on Linux nodes, executes Ping, Traceroute, MTR, NextTrace, iPerf3, and download tests, and handles enrollment, configuration sync, TLS, heartbeats, and self-updates.

Linux `amd64` (`x86_64`) and `arm64` (`aarch64`) are supported. See the [main project documentation](../README.md) for the complete deployment and Controller configuration.

## Quick install

In the Controller admin panel, open **Nodes → Add Node** and copy the generated command for that node. Its format is:

```bash
curl -fsSL 'https://lg.example.com/_agent/download?init-key=lginit_xxx' \
  | bash -s -- -k 'lg.example.com/lginit_xxx'
```

Run it as `root` on the target node. The Init Token is only for initial enrollment; do not reuse or disclose it.

The installer detects the CPU architecture, downloads and verifies the Agent, and starts initialization. The Agent then enrolls the node, stores its own Node Token, selects probe tools, creates an initial TLS certificate, installs a system service, and starts.

Default paths and listener:

| Item | Default |
| --- | --- |
| Install directory | `/opt/looking-glass` |
| Data directory | `/opt/looking-glass/data` |
| HTTPS listener | `:443` |
| Service name | `hlg-agent` |

The admin panel also provides architecture-specific manual download, SHA-256 verification, and initialization steps for environments that cannot run the piped installer.

## Requirements

- Linux `amd64` or `arm64`; systemd or OpenRC is recommended.
- The service runs as `root` by default. A non-root installation needs at least raw-socket and low-port capabilities:

  ```bash
  sudo setcap cap_net_raw,cap_net_bind_service+eip /path/to/hlg-agent
  ```

- The Controller must be able to reach the Agent's HTTPS port. Visitor browsers also need to reach this port when running latency probes. Check the host firewall, security groups, upstream ACLs, and NAT mappings.
- Deploy the Controller and create the node in the admin panel before installing the Agent.

System `ping`, `mtr`, and `traceroute` binaries also need their respective permissions.

## Initialization

Initialize with the Init String generated by the Controller:

```bash
sudo ./hlg-agent init -k 'lg.example.com/lginit_xxxxxx'
```

A Controller port can be included:

```bash
sudo ./hlg-agent init -k 'lg.example.com:8443/lginit_xxxxxx'
```

Common options:

| Option | Description |
| --- | --- |
| `--path` | Install directory; defaults to `/opt/looking-glass` |
| `--data-dir` | Data directory |
| `--port`, `-p` | HTTPS port; shorthand for `--bind :PORT` |
| `--bind` | Full listen address |
| `--service` | `auto`, `systemd`, `init.d`, or `none` |
| `--service-name` | System service name |
| `--name`, `--binary-name` | Installed binary name |
| `--user` | Existing service user; initialization never creates a user |
| `--yes` | Use defaults for unspecified options without prompting |
| `--install-deps-yes` | Install every missing runtime dependency automatically |

Unattended installation example:

```bash
sudo ./hlg-agent init \
  -k 'lg.example.com/lginit_xxxxxx' \
  --path /opt/looking-glass \
  --port 443 \
  --service auto \
  --yes
```

Non-interactive initialization automatically selects available tool sources.

## Probe tools

The Agent supports these tools and sources:

| Tool | Available sources |
| --- | --- |
| Ping | System command, built-in Go implementation |
| Traceroute | System command, built-in Go implementation |
| MTR | System command, built-in Go implementation |
| NextTrace | System command, Agent-managed download |
| iPerf3 | System package, Controller-provided static build |

Automatic mode prefers commands found in the system `PATH`, then uses an Agent-managed build or a built-in implementation when available. The selected paths are recorded in `agent.json`, so every job does not have to search again.

### Ping, MTR, MPLS, and ECMP capabilities

| Probe | IPv4 / IPv6 | Latency and loss | ECMP | MPLS |
| --- | --- | --- | --- | --- |
| Ping | Supported | Per-reply RTT, TTL / Hop Limit, packet loss, and min/avg/max/mdev | Not applicable | Not applicable |
| Built-in Traceroute | Supported | RTT for each responding address | Samples three stable UDP flows per hop and marks multiple responders as `[ECMP]` | Parses Label, Traffic Class, and MPLS TTL from ICMP extensions |
| System Traceroute | Supported | RTT for each probe | Shows multiple responding addresses at the same hop | Uses `-e` to request ICMP extension output; the Controller parses MPLS fields |
| Built-in MTR | Supported | Continuously reports Loss, Snt, Last, Avg, Best, and Wrst | Currently follows one stable flow and does not identify ECMP separately | Does not currently emit an MPLS stack |
| System MTR | Supported | Continuously emits `--split` statistics | The current output pipeline does not label ECMP branches | The current command does not enable MPLS output |

The built-in Traceroute keeps the source and destination ports fixed for each sampled flow, preserving that flow's hash across TTL values. If its three flows receive more than one response address at the same hop, the result includes `[ECMP]`. When routers return RFC 4884 / RFC 4950 ICMP extensions, it also renders MPLS information such as:

```text
[MPLS 404160/TC0/TTL1]
```

These features depend on routers returning the relevant ICMP responses and extensions. The absence of `[ECMP]` or `[MPLS ...]` only means that the limited sample did not observe it; it does not prove that the path has no ECMP or MPLS.

### Actual system MTR command

When a job is configured to use system MTR, the Agent runs:

```bash
# IPv4
TERM=dumb mtr -4 --split -n <target>

# IPv6
TERM=dumb mtr -6 --split -n <target>
```

- `-4` / `-6` fixes the address family.
- `--split` continuously emits results for real-time forwarding by the Controller.
- `-n` disables reverse DNS to avoid slow lookups and unstable output widths.
- `TERM=dumb` produces output suitable for a non-interactive terminal.

Neither the current system nor built-in MTR output provides the ASN data required by the frontend. The Agent reports hop IPs together with loss and latency statistics; the Controller then performs a bulk Team Cymru Whois lookup for the ASN, prefix, registry, country, and AS/BGP organization before sending the enriched structured result to the frontend.

When private-target protection is enabled, the Agent resolves and validates the target first, then passes the selected IP address to the probe command to prevent a second DNS lookup during execution.

If the MTR source is `builtin`, the Agent starts no external `mtr` process and continuously runs its built-in Go probe instead.

### Other system commands

For troubleshooting, the main arguments used in system-tool mode are:

```bash
ping -4 -O -c 5 -W 2 <target>          # Use -6 for IPv6; jobs may request 10 probes
traceroute -4 -n -w 2 -e <target>     # Use -6 for IPv6
nexttrace --ipv4 --map -g en <target> # Use --ipv6 for IPv6
```

### NextTrace

The Agent supports [NextTrace / NTrace-core](https://github.com/nxtrace/NTrace-core). In download mode, it obtains release metadata from the Controller, downloads the official binary for the current architecture, verifies its SHA-256 digest, and saves it under `deps/` in the data directory. The Controller only accepts download URLs matching `github.com/nxtrace/NTrace-core/releases/`.

### iPerf3

The Agent prefers an existing `iperf3` binary and can install it through the system package manager. When package installation is unavailable, it can use static Linux `amd64` and `arm64` builds supplied by the Controller. The Agent verifies their SHA-256 digests against the dependency manifest.

## Tool management

Show the effective source and status of every tool:

```bash
hlg-agent deps check
```

Configure sources interactively:

```bash
sudo hlg-agent deps config
```

Sources can also be selected non-interactively:

```bash
sudo hlg-agent deps config mtr --source builtin
sudo hlg-agent deps config nexttrace --source download
sudo hlg-agent deps config iperf3 --source system
sudo hlg-agent deps config traceroute --source path --tool-path /usr/local/bin/traceroute
```

`--source` accepts `auto`, `system`, `builtin`, `download`, `path`, `install`, and `nothing`; not every source applies to every tool. Restart the Agent after changing a source. Interactive mode offers to restart it immediately.

Other commands:

```bash
sudo hlg-agent deps install nexttrace iperf3
sudo hlg-agent deps upgrade
sudo hlg-agent deps builtin ping traceroute mtr
```

## Docker

The repository provides a [Dockerfile](Dockerfile) and [compose.yaml](compose.yaml). From the `agent/` directory, run:

```bash
mkdir -p /srv/hlg-agent/data

LG_INIT_STRING='lg.example.com/lginit_xxxxxx' \
LG_AGENT_DATA_DIR=/srv/hlg-agent/data \
LG_AGENT_PORT=443 \
docker compose up -d --build
```

Compose builds the local `hlg-agent:local` image, adds the `NET_RAW`, `NET_ADMIN`, and `NET_BIND_SERVICE` capabilities, and maps host port `${LG_AGENT_PORT:-443}` to container port `443`.

The container data directory is `/var/lib/hlg` and must be persisted. `LG_INIT_STRING` is only used on the first start when no node identity exists. Later starts load the persisted Node Token and configuration.

The image includes `curl`, `iperf3`, `iputils`, `mtr`, and `traceroute`. The Agent still manages optional tools such as NextTrace.

## TLS certificates

The Agent serves HTTPS itself. Initialization creates a self-signed ECDSA certificate, so an existing Nginx or Caddy installation is unnecessary.

The Controller can deliver an ACME-issued or manually imported certificate. The Agent stores the active certificate as `tls.crt` and `tls.key` in the data directory and loads an updated certificate for new TLS connections without reinstalling the Agent.

## Enrollment, configuration, and security

Initial enrollment uses a one-time Init Token. After enrollment, the Agent stores its own Node ID and Node Token. Configuration sync, heartbeats, and update checks use this node identity.

Runtime configuration from the Controller is signed with Ed25519. The Agent accepts it only after signature verification. It covers allowed tests, job timeouts, output limits, download limits, iPerf3 sessions, port ranges, and related policy. Do not edit `config.json` to bypass these policies.

The Agent also rechecks each target before execution. When private-target protection is enabled, private addresses, unresolvable targets, and targets that do not match the requested address family are rejected.

## Agent updates

Check for or install a Controller-published build:

```bash
hlg-agent upgrade --check
sudo hlg-agent upgrade
```

The update descriptor contains the Build ID, target architecture, size, SHA-256 digest, Node ID, expiration, and Ed25519 signature. The Agent verifies all fields before atomically replacing its binary and restarting the service. If the restart fails, it restores the backup binary.

Reinstall the current build:

```bash
sudo hlg-agent upgrade --force
```

## Health checks and service management

For installation, configuration, certificate, or probe failures, start with:

```bash
hlg-agent doctor
hlg-agent deps check
hlg-agent service status
```

Service control commands:

```bash
sudo hlg-agent service start
sudo hlg-agent service stop
sudo hlg-agent service restart
```

`--service auto` selects systemd or OpenRC. With `--service none`, the Agent does not install a system service; manage the `hlg-agent run` process separately.

## Local probes

The `probe` subcommand directly runs the Agent's built-in Go probe. It is useful for checking raw-socket permissions and the built-in implementation; it does not use the system-tool source configured for jobs.

```bash
hlg-agent probe ping 1.1.1.1
hlg-agent probe -6 ping 2606:4700:4700::1111
hlg-agent probe traceroute 8.8.8.8
hlg-agent probe mtr 1.1.1.1
hlg-agent probe -6 mtr 2606:4700:4700::1111
```

IPv4 is the default. `-4` and `-6` are mutually exclusive, and local probes also require `CAP_NET_RAW` or root.

To test the system MTR binary itself, run the applicable `TERM=dumb mtr ...` command shown above. To see which implementation Agent jobs will use, run `hlg-agent deps check`.

## Logging and environment variables

Log levels are `debug`, `info`, `warn`, and `error`:

```bash
hlg-agent run --log-level debug
hlg-agent run --log-file /var/log/hlg-agent.log
```

Common environment variables:

| Variable | Description |
| --- | --- |
| `LG_CONTROLLER` | Controller address |
| `LG_INIT_STRING` | Full Init String for initial enrollment |
| `LG_INIT_TOKEN` | Init Token |
| `LG_NODE_TOKEN` | Node Token |
| `LG_NODE_ID` | Node ID |
| `LG_BIND` | Agent listen address |
| `LG_DATA_DIR` | Data directory |
| `LG_PUBLIC_IPV4` / `LG_PUBLIC_IPV6` | Manually reported public addresses |
| `LG_FRONTEND_ORIGIN` | Allowed frontend origin |
| `LG_LOG_LEVEL` / `LG_LOG_FILE` | Log level and output file |
| `LG_IPERF_DEBUG_OUTPUT` | Expose raw iPerf3 debug events on the control WebSocket |

These variables normally require no manual setup when using the command generated by the admin panel.

## Local files

A standard installation writes its runtime record to `/opt/looking-glass/agent.json` and stores persistent data under `/opt/looking-glass/data`. Docker places both in the persisted `/var/lib/hlg` mount.

| File or directory | Purpose |
| --- | --- |
| `/opt/looking-glass/agent.json` | Local runtime options, installation layout, and tool choices |
| `<data-dir>/node-token` | Node authentication token |
| `<data-dir>/config.json` | Signed configuration from the Controller |
| `<data-dir>/tls.crt` / `tls.key` | Active TLS certificate and private key |
| `<data-dir>/deps/` | External tools managed by the Agent |
| `<data-dir>/deps/deps-manifest.json` | Local integrity record for downloaded tools |

Deleting the data directory removes the node identity and usually requires a new Init Token and enrollment. Back it up first when the identity or certificates must be retained.

## Building from source

```bash
cd agent
CGO_ENABLED=0 go build -trimpath -ldflags='-s -w' -o hlg-agent ./cmd/hlg-agent
```

Cross-compile for both supported targets:

```bash
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build \
  -trimpath -ldflags='-s -w' -o hlg-agent-linux-amd64 ./cmd/hlg-agent

CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build \
  -trimpath -ldflags='-s -w' -o hlg-agent-linux-arm64 ./cmd/hlg-agent
```

Release builds also set the Build ID with this linker option:

```text
-X hlg/internal/runtime.BuildID=<build-id>
```

## Uninstall and command reference

Uninstall the Agent:

```bash
sudo hlg-agent uninstall
```

Uninstall stops and removes the service as well as the local installation files and data. Back up the data directory first if the node identity or certificates must be retained.

| Command | Description |
| --- | --- |
| `hlg-agent init` | Enroll, initialize, and install the Agent |
| `hlg-agent run` | Run the Agent in the foreground |
| `hlg-agent doctor` | Check installation and runtime health |
| `hlg-agent service` | Manage the system service |
| `hlg-agent deps` | Inspect, install, or configure probe tools |
| `hlg-agent probe` | Run a built-in network probe directly |
| `hlg-agent upgrade` | Check for or install an Agent update |
| `hlg-agent uninstall` | Uninstall the Agent |
| `hlg-agent version` | Show the version and Build ID |
| `hlg-agent help` | Show command help |
